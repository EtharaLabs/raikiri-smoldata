Code facts (frozen source). In `lib/schemes.js`, `mailtoParse` splits the query on `&`, takes each field's `name` as the raw text before `=` (the whole field when it has no `=`), and compares that raw `name` with `'to'`, `'subject'` and `'body'` using `===`; any other field is stored as `headers[decodeHex(name)] = decodeHex(value)`. `mailtoSerialize` copies `component.headers`, sets `headers.subject` and `headers.body` from the component properties when they are truthy, and writes every field as `encodeWithAllow(name, HFNAME) + '=' + encodeWithAllow(String(value), HFNAME)`. `encodeWithAllow` keeps an existing `%XX` sequence as an escape, so a decoded name that contains `%74` is emitted unchanged. `decodeHex` decodes `%XX` sequences. Top-level `parse`, `serialize`, `normalize` and `equal` in `index.js` reach these two functions through the mailto scheme handler.

The graded defect. Because the comparison runs on the still-encoded, case-sensitive name, a field named `%74o`, `%73ubject`, `TO` or `Subject` is kept as a generic header on the first parse, and on serialization a decoded generic name containing a percent sequence (`%74o`) is emitted so that the next parse decodes it again into a reserved name. Field names are case-insensitive; a reserved spelling with any letter case in `headers` is not folded into the recipients, subject or body when serializing. The recipients, subject, body and headers a caller sees can change between parse and parse-after-serialize. A complete repair corrects both directions: `mailtoParse` decodes each field name once and compares it case-insensitively, and `mailtoSerialize` encodes every percent sign in a header field name as data (`%25`) and folds reserved spellings of any case from `headers` into the dedicated fields, while header values keep their existing encoding. The code that must change is `mailtoParse` and `mailtoSerialize` in `lib/schemes.js` (or helpers only they call). The second weakness, of the same input-validation kind and graded with a small share, is in `canonicalizeHost` in `index.js`. For a domain-host scheme (`http`, `https`, `ws`, `wss`, or the `domainHost` option) whose host is not a simple domain, it sets `parsed.host = new URL('http://' + parsed.host).hostname` without checking that the WHATWG parser read the whole input as a host. The RFC 3986 parse lets `@` and raw TAB, LF or CR into the host group, and the WHATWG parser treats `@` as a userinfo delimiter and strips TAB, LF and CR, so `http://user@ev<TAB>il.example/path` is reported with host `evil.example` and `http://a@b@evil.example/` with host `evil.example`, with no `error`; `normalize` and `equal` follow that host, and `resolve` calls the same `canonicalizeHost` on the resolved component. A correct repair makes such a host fail closed (an error, an unchanged `normalize`, `equal` false, `resolve` throwing) or otherwise keeps the reported host from changing; rejecting the forbidden characters before the WHATWG call, or refusing a WHATWG result that is not a bare hostname, are both correct. A single `@` that separates userinfo from the host is legitimate and stays accepted. The RFC 3986 parse ends the userinfo at the first `@`, so for `http://user@example.com/` the userinfo is `user` and the host group is `example.com`; the host group holds an `@` only when the authority carries a second `@`. A repair that refuses an `@` inside the host group therefore does not reject a URI whose authority carries userinfo, so it does not make R18 "yes". Other weaknesses in the tree (for example in `lib/utils.js`) are not graded.
